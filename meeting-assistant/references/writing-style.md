# 写作要求与改写示例

## 内容是主体

写成读者可以直接使用的知识文档，而不是“某人讲过什么”的报告。不需要重复说明资料来自录音、课程或聊天。

| 避免 | 优先写法 |
| --- | --- |
| 老师说，前端负责用户界面。 | 前端负责用户看得见、能操作的页面。 |
| 老师分享了一个跨专业团队的创业故事。 | 举例：一个跨专业团队围绕特定需求开发产品…… |
| 这部分主要传达的是产品需要数据库。 | 需要长期保存账号和历史记录时，应配置相应的数据存储。 |
| 回看位置：第 2 段 18:00—24:00。 | 默认删除；仅在用户要时间索引时单独提供。 |
| 录音中的排名仅代表当时的体验，不作为购买建议。 | 从个人体验看，工具 A 更适合……，工具 B 的优势是……。仅使用来源支持的体验。 |
| 老师先介绍了架构，然后介绍部署。 | 按知识关系组织“产品架构”“开发与部署”等章节。 |

## 具体的例子

例子不是一句“有个案例”，也不是没有细节的感想。尽量交代：

1. **背景／目标**：谁面临什么问题。
2. **做法**：采取了什么方案。
3. **结果／状态**：做成了什么、遇到了什么、是报价还是已成交。
4. **启示**：这个例子帮助理解哪个概念。

例如，虚构素材“一个团队先做了文档摘要接口，后来做页面并增加历史记录”，可以整理为：

> **举例：把文档摘要功能变成学习工具。**
>
> 一个团队已经能用 API 生成文档摘要，但用户需要手动调用接口。团队先增加上传页面，再加入登录和历史记录，用户便能在网页中完成上传、查看和复习。
>
> 这个例子的关键，是把核心能力、操作入口与长期数据连接起来。

实际案例的角色、金额、结果和因果必须来自资料；上面的虚构示例不能混入真实笔记。

## 观点与不确定性

- 保留工具体验中的主观口吻，但不添加未发生的亲测。
- “认为值得”“可能获得”“收到收购意向”不能改成“证明有效”“已获得”“已成交”。
- 不用删掉“老师说”的方式，把预测、评价和不完整猜测改成公认事实。可以使用“个人判断是……”“一种可考虑的做法是……”。
- 不明确的工具名先用功能类别表达，例如“工作流平台”；有课件证据后再替换成具体名称。
- 不重要且无法确认的版本号、报价可以不写；影响结论的数字应明确保留待确认状态。
- 资料之间存在实质冲突时保留问题，不通过漂亮措辞掩盖。

## 标题与组织

```markdown
# 与内容相符的总标题

## 一、目标与核心问题

直接解释要解决的问题。

## 二、概念和关系

**关键概念**

解释含义，再展开术语。

## 三、方法与案例

**举例：具体案例名称。**

写明背景、做法和结果。
```

这只是可变的结构示意，不是每篇必须包含的固定目录。复用用户已有的合理结构，避免为了统一模板打散内容。

会议模式下，以会议目标、关键讨论、已确认决议、行动项、未决问题为合适候选。不要把授课里的操作示例写成某个与会者已承担的任务。
